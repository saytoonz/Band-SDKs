# Veepoo device compatibility

Evidence is scoped to HBand 11.0.50 (11050) and GBand 2.3.14 (377) unless attributed to a public document. See [APK provenance](apk-provenance.md). Apple Watch Series 8 and WHOOP 4.0 are the only devices available and are outside this protocol investigation. No compatible device has been tested.

## Confirmed static evidence

| Area | HBand | GBand |
| --- | --- | --- |
| Advertised identity | `util.VpBLEDeviceScanRecordManager` reads the UTF-8 complete local name (AD type `09`). Default discovery recognizes Veepoo markers and excludes its two custom-brand prefixes `F9 F9` (Veepoo Health) and `A0 A0` (TLS Watch). Its manufacturer-specific AD (`FF`) branch recognizes `F8 F8` when the data has more than two bytes. Its complete 16-bit UUID list branch checks the first pair for `FF FF`, `0D 18`, `E7 FE` or `01 00`. There is also an explicit opt-in brand filter. | `VPBleCenter.handleSearchResult` rejects the name sentinel `NULL` and uses the runtime name for the display/device object. `VpBleByteUtil.isBeyondVpV2` checks the first two octets of AD type `FF` for `F8 F8`. The scan parser requires at least two manufacturer bytes. |
| Model number and firmware | `BluetoothService.connectSuccess` gets the model number from the `A1` response at bytes 4–5 (BE) and the firmware components at 6–8, with an optional test component at 9. `BleInfoUtil` falls back to the `A4` device-number path for response numbers 20 and 101. Model number 6592 has a blood-glucose-specific branch. None of these numbers is mapped to raw PPG or RR support. | `p001if/v1.java` and alternate `f.java` read the model and firmware components at the same offsets. `com.veepoo.protocol.r` has a post-authentication exception for model 2501 and a test version `00.00.00.00` condition. No raw feature is implied. |
| Version gates | The HBand `DeviceFunctionHandler.parseA7Package2` takes byte 10 as the history protocol type. `BleReadManager.readOriginal` uses the DF handler for types 3 and 5 and the legacy handler otherwise. No minimum firmware was found for RR or raw PPG. | `p001if/y.java` reads origin protocol version from byte 10 of `A7` device function report package 2. `OriginDataReader.createProgressListener` branches for versions 3 and 5. The scan method name `isBeyondVpV2`, SDK constant `VPPROTOCOL_TYPE = 15`, and origin protocol version are separate signals. None was traced as a raw PPG or RR gate. |
| Generic PPG flag | `OriginalDFHander.setPpgs` supplies values that the half-hour aggregation filters and logs as pulse rates, including a 30–200 plausibility range. This path does not establish waveform access. | `p001if/t.java` reads PPG switch support/status from offset 16 in `B8` custom-settings page 0 (0 unsupported, 1 open, 2 closed). `VpSpSaveUtil` persists support and open state. `HealthMonitorViewModel` consumes `isSupportPPG()`. There is no trace from this general settings flag to `readPPGRawData` or the raw-stream subscription. |
| Raw operations | `RRIntervalManager` exists, but no caller was located and the general dispatcher routes `70` to GPS. No raw waveform reader was established. | The SDK has stored `EB` and live `EB 03` PPG entry points and a separate `70` RR reader. Their request methods have no located model or firmware allowlist. `EB 01` reads/reports a raw-test switch, which differs from the generic PPG flag. `70` block number zero exits the handler. No app-screen caller or trusted model mapping was found for either stored read. |

The manufacturer prefixes are bytes consumed by these classifiers. The APK checks do not establish an assigned company identity. The model number comes from a post-connect response and is distinct from the advertised name, which can be customized. No authoritative mapping was found from raw-capable project identifiers to numeric model IDs, advertised names, hardware revisions or qualifying firmware versions.

## Evaluation shortlist

| Priority | Model or project | Basis and expected scope | Open before relying on it |
| --- | --- | --- | --- |
| 1 | **Veepoo JH58 with raw-PPG project firmware** | Strongest feature-specific candidate. Veepoo's public Android documentation explicitly limits the PPG test feature to the customized JH58 project and documents the same history API, modes and live callback family found in GBand. This is evidence for stored/live green PPG and acceleration on the correct firmware. [Veepoo Android SDK documentation](https://github.com/HBandSDK/Android_Ble_SDK/wiki/VeepooSDK-Android-API-Document#jh58-ppg-test-function) | Confirm the orderable SKU, firmware, model ID, advertised name, ability to bind with GBand 2.3.14 and `EB` support in that build. RR/PPI support is unknown. |
| 2 | **Veepoo G08W project hardware** | GBand's `setG08WProjectPPGLightDataCallback` subscribes to `f0020002`. Its callback maps `80`, `83` and `84` to three light channel IDs. `startDetectSPO2HForG08WProject` ties a related callback to SpO₂ measurement. This is a project-specific live optical signal lead. | Verify an obtainable SKU, firmware and transfer setup. No evidence links G08W to stored `EB`, `70`, channel wavelengths or an advertised name. |
| 3 | **VIGOR GPS Smart Band** | The device manual identifies `VIGOR` in the G BAND pairing list and describes in-app pairing plus data synchronization. This is a retail lead for baseline GBand discovery, binding and derived measurements. [VIGOR user manual](https://ae-pic-a1.aliexpress-media.com/kf/S5f42145d4aaa4345bf39873a42359e2at.pdf) | Verify hardware revision and firmware, exact Android package/build and supported measurement records. No evidence links VIGOR to JH58, G08W or raw RR. |
| 4 | **Veepoo Watch RIG** | Veepoo's original product write-up mentions H Band for sleep, and the manufacturer also identifies Veepoo Health as RIG's customized app. It is a lower-priority HBand baseline lead. [Veepoo product write-up](https://www.veepoo.net/post/veepoo-health-monitoring-smart-watch-fully-protects-your-health), [Veepoo companion app page](https://www.veepoo.net/) | Confirm the app and firmware pairing for the exact variant. Optical sensors, ECG waveforms and HRV features provide no evidence of raw PPG or RR transfer through these APKs. |

JH58 is the first purchase candidate to qualify with Veepoo. A vendor demonstration or trace should identify the exact model, firmware, companion package and successful raw read. If only retail VIGOR can be sourced, its evidence supports an interoperability baseline. There is no purchase-ready candidate specifically for RR retrieval.

## Hardware validation order

1. Record packaging/SKU, factory firmware, app build, Android version and whether the device has previously been paired. Before firmware updates, capture local name, raw advertisements, manufacturer data, GATT UUIDs and characteristic properties.
2. Record vendor-app first bind, any physical confirmation and reconnect after app restart. Note when the CCCD write succeeds and whether an OS bond prompt appears. Redact bind values and device identifiers from any replay fixtures.
3. Capture one supported JH58 collection session. Correlate raw-test status, `EB 02` start, header, numbered fragments, block acknowledgment and completion. Compare at least two block sizes, including repeated sync and interruption. Preserve CRC fields and payloads to evaluate coverage and integrity. Use the vendor's documented feature or a vendor-supplied recording if the installed app exposes no control.
4. Capture a separate live optical and motion session, including an idle-to-movement transition. Check trailer bytes, packed signed values, channel IDs, sample cadence and start/stop responses on the actual characteristics.
5. For authorized RR-capable hardware, record each day selector against known device clock settings, a zero-block result, a multi-block result and a repeat read. Compare against a separately timestamped reference to determine interval boundaries, duration units and timing origin. Record whether the test hardware actually exposes this operation.
6. Replay sanitized traces offline, pin fixtures to the model/firmware and APK hashes, then verify a minimal, plugin-neutral GATT adapter using the documented binding flow. Keep sample timing, units, skin placement and quality unset until measured or documented.
